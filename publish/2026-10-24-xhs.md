# 拆解 agent-usage-guard：拦截子智能体失控

GitHub 上最近冒出不少管大模型上下文和额度的项目。今天看的是 agent-usage-guard（星数 60，日均涨星 16），专治 AI 智能体失控把额度跑爆。

多智能体工作流里，大上下文、快速工具循环、并行智能体加上盲目重试，很容易把开销放大。作者记了一次测试：给 Claude Code 发个指令，十分钟内触发 394 次子智能体调用，341 个并发，吃掉 8400 万上下文 Token。Hacker News 上的相关讨论也有类似案例，比如单次提示生成 339 个子智能体，递归几下半周配额就没了。

这东西是个 Claude Code mod。在 v2.1.287 及以上版本跑 `/plugin marketplace add rbartoli/agent-usage-guard` 这类命令就能装。它是在执行前拦动作，不是事后算账。默认规则写得很死：5 小时窗口用量到 80% 弹人工确认，到 95% 直接拒；全局并发子智能体上限 4 个；每 10 分钟启动或恢复的智能体上限 12 个。README 里列了 `demo/scripted-api.ts`、`demo/render.sh` 还有 `demo/fixture/northstar-api` 这些文件，能用本地脚本复现 UI 演示，不花真钱。

看实现逻辑能感觉到，这是有真实工程基础的工具，不是拿提示词糊的。它能在本地管状态，存用量计数和粗略区间，不碰提示词文本和模型输出。容错做得也规矩：钩子挂了事件照跑，保护机制不至于把开发者会话卡死，只有没法及时判断时才拒掉智能体启动。

对比最近看到的 Jozu Agent Guard 和 SandboxAQ 的 AQtive Guard，那俩更偏企业级安全、沙箱隔离和合规。agent-usage-guard 就是给本地开发者挡配额的。我们追踪的同类工具里，caveman 和 headroom 主要搞上下文压缩，agent-usage-guard 直接管调用和 Token 消耗拦截，相对更直接。

局限也明显，死绑 Claude Code 最新 mod 生态，跨平台差点意思。而且那套固定并发和时间窗口阈值，真遇到死磕并行智能体的复杂科研编排，估计得手动调参，不然容易误拦。

说白了就是给本地 API 配额加硬熔断，挺实在的工程实现。
