# 拆解问题定框：动手前先证伪问题本身

现在多数 AI 编程工具都在卷代码、文档或测试的生成速度，很少有人管动手前的问题定义对不对。ordinary-s/falsify-the-problem 就是干这个的。项目目前 102 颗星（我们于 2026 年 9 月 18 日首次追踪，日均涨星 +3），是个开源 Agent Skill，主要在写代码和调试时做问题定框与假设检验。

GitHub 页面说 falsify-the-problem 的核心是"问题定框"（problem framing）和"假设检验"（assumption testing）。思路来自波普尔的可证伪性理论：好假设得能被证伪。名字也是这意思——解决问题前，先试着证伪问题本身。不过这次 README 抓取失败了，没法看它的文件结构、CLI 或者有没有 scripts/tests/CI。单看有限信息，这算是个跨编码和调试场景用的 skill。

没法确认它有没有完整工程实现。看定位更像提示词和技能框架，把可证伪性思维包成 Agent 能调用的 skill。我们把它归为"Claude Code skill / prompt 模式"，评分 9/10。

同类项目里，搞学术和科研的技能包大都在卷产出（生成论文、整理文献等），falsify-the-problem 只管问题定框，不碰具体产出。主打"先想清楚再动手"，我们已有项目里没重复的。

README 拉不到，外面的人很难快速评估它实现得有多深。问题定框很吃人的认知判断，Agent Skill 到底能帮上多少忙还得打问号。Reddit 上 r/PhilosophyofScience 讨论过，可证伪性常被当成"跟观察矛盾就算被证伪"，其实逻辑复杂得多，这种理解偏差直接套到工程里容易出事。

写代码前习惯先拆解假设的话，可以看看这个 skill。工程质量等 README 恢复了再说。
