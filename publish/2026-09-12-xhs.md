# 拆解 Humanizer：25 条模式如何改写 AI 文风

过去一年，GitHub 上冒出过几十个项目，都在解决同一个问题：怎么把一段读起来像 AI 写的文字，改得更像人写的。今天讲的 blader/humanizer 是其中星数最高的之一，截至 2026 年 7 月 2 日约 46,923 星，日均涨星约 279。不过它不是唯一值得聊的。

这领域的问题很具体。语言模型写的是最可能出现的下一个词，默认选那种能覆盖最广读者和主题的表达，于是留下一堆可识别的痕迹。维基百科的「Signs of AI writing」页面把这些痕迹整理成了条目，Humanizer 的 README 直接引用了它。

拆一下它的实现。安装走 Skills CLI：`npx skills add blader/humanizer --global`，去掉 `--global` 就只装进当前项目，还能用 `--agent <name>` 指定哪些 agent 接收。Claude Code 2.1.142 及以上可以改用插件方式安装，调用名从 `/humanizer` 变成 `/humanizer:humanizer`。手动安装就是把 `SKILL.md` 复制进 agent 的 skill 目录。整个仓库的核心就是这份 Markdown，README 里写得很直白：「因为它只是 Markdown，所以任何支持 skills 的 agent 都能用」。

真正的内容是 25 条模式，按强度和频率编号。前五条单次出现就能构成修改理由，标了 weak alone 的模式得在一段里同时出现多个才算数。它们分成几组：A 组「铺垫代替陈述」，包括 Not X but Y、单行收尾和戏剧化残句、听起来深刻的格言、进入正题前的起跑、和没人争论；B 组「按规则制造的节奏」，包括强制三段式、重复句首、把破折号当万能连接符等。

工作流程也写在 README 里：先标出所有命中的痕迹并按强弱排序，起草一版不把原文结构当固定前提的重写，再把草稿对照模式清单和原 claim 核对，最后产出终稿。它明确承诺不编造：人名、数字、日期、引语、引用这些事实细节必须来自原文或作者，缺细节时提问而不是编。粘贴文本会展示全过程——初稿、对仍显生硬之处的简短批评、终稿；指向文件则只改散文，代码、数据、frontmatter 和链接目标不动。

工程含量判断：这是说明书和提示词包装，不是真实工程。依据是 README 里没有任何测试、CI、脚本或构建产物的证据，安装方式全围绕把 SKILL.md 放进目录，运行逻辑由宿主 agent 的模型执行，仓库本身不包含能独立运行的代码。它的价值在于把写作规范整理成结构化、可复用的清单，而不是工程实现。

横评看定位。op7418/Humanizer-zh 是核心文件的中文翻译加工具补充，服务中文写作场景；NulightJens/humanizer-stack 做两遍流水线，把表层改写和结构改写分开。三者面向的是不同语言、不同深度需求的用户。

局限也明显。25 条模式的判据来自对 AI 文风的观察，本身就是主观清单，改写的质量取决于宿主模型而非项目代码。当它被用来规避 AI 检测时，检测方同样可以更新判据，这是一场没有终点的对抗。

一句话收尾：它把「像人写的」拆成了可逐条核对的清单，但清单本身仍然由模型来执行。
